# 环境体检（dsh-env-doctor）

你有一个工具 `dsh_env_doctor`。它替用户查 Windows 上的 DSH 环境，把「坏了、为什么坏、下一步敲什么」说清楚。

## 什么时候用

- 用户说「体检一下」「环境是不是有问题」「帮我看看为什么……」。
- 用户遇到写文件被拒、`bash` 起不来、`npm`/`pnpm` 报「禁止运行脚本」、装东西卡在网络上、`gh` 凭据失效。
- 在做可能受环境影响的事（装依赖、跑构建、推 GitHub）之前，想先确认环境健康。

## 怎么调

| 目的 | 参数 |
|---|---|
| 全面体检（默认，只读） | `{ "mode": "check" }` |
| 只查某几组/某项 | `{ "mode": "check", "checks": "A" }` 或 `{ "checks": "A.1,C.4" }` |
| 解释某个结论 | `{ "mode": "explain", "input": "A.3" }` 或 `{ "input": "C:\\Users\\...\\file.txt" }` |
| 修一条（必须先得到用户明确同意） | `{ "mode": "fix", "fix": { "id": "C.4", "confirm": true } }` |

报告默认写到 `<workspaceRoot>/.dsh-doctor/report-<时间戳>.md`，工具返回值里的 `reportPath` 是确切路径。

## 怎么读结论

- `ok` 通过；`warn` 需注意（不阻塞）；`fail` 失败（要处理）；`undiagnosed` **说不准** —— 通常是沙箱/权限导致观测失败，既不算好也不算坏。
- `level` 是危险等级，不是修复难度：`high` 说明放着不管会持续挡路。
- 每条 `fail`/`warn` 都带 `fix.command`：这就是要给用户看的「下一步」。`fix.autoApplicable` 为 true 的只有 B.2 / C.4 / D.1 / E.3。

## 转述规则

1. 先说总体结论（通过几项、几项要注意、几项失败、几项说不准），再给需要动手的条目。
2. 每条按「现象 → 为什么 → 下一步命令」讲，命令原样给出，别改写、别翻译成语义。
3. `undiagnosed` 必须如实说「这项这次判断不了」，不要猜成通过或失败。
4. **不要**说「已经修好了」——除非工具返回的复检结果是 ok。

## 修复的两道门

- 第一道：用户在对话里明确同意（「修吧」「改吧」）。没同意就只给命令。
- 第二道：调用时传 `fix.confirm = true`（护栏会拦下没传的）。
- `A.3`（ACL）、`F.1`（UAC/安装通道）、`F.2`（注册表长路径）**永远只给命令**，不做。
- ACL 相关一律交棒内置技能 `diagnose-windows-sandbox-acl`，不要自己拼 icacls。

## 不要做

- 不要为了「看起来更全面」而自己发明检查项：目录是 17 项，写死在代码里。
- 不要在没有 `fix.confirm` 的情况下反复试 `mode:"fix"` —— 护栏会一直拒。
- 不要把报告写到工作区外（工具会直接抛 `E_OUT_OUTSIDE_WORKSPACE`）。
